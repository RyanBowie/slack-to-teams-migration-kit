What can it migrate today?

Support is based on the application's source and behaviour, not just its name in Slack. The supplied recipes expect trusted JavaScript/Node source with a separable business service and a reviewed acceptance baseline. Other patterns need engineering before they can use this workflow.

The source contracts are intentionally narrow

The bot job requires domain.mjs, slack.mjs, an explicit identity map and command/action acceptance scenarios. The supplied replay instantiates createService(), registers registerSlackHandlers(app, { service }), invokes the command/action callbacks and compares synchronous snapshot() results. The service interface must match the reviewed source contract; merely having a Slack manifest or a Node project is not enough.

The Home recipe additionally expects synchronous list/decide execution with the reviewed approval service shape: request versions, requests/audit responses and trusted server-side actor handling. Its generated adapter is handleDashboard(service, actorId, input). An incompatible service needs another reviewed recipe rather than speculative conversion.

“Supported” means the pattern has a defined generation and verification path. It does not guarantee first-pass model success, complete business equivalence or production readiness. Unsupported entries are reported as blocked/manual-review/vendor-alternative work, not silently marked migrated.

Before the first paid model call

What you need to bring.

Source and business evidence

  • Authorised application source, selected through a file allowlist; not a message export or just an installed-app list.
  • An app owner, criticality, declared capabilities and known dependencies.
  • Reviewed acceptance cases covering normal use, denied roles, privacy, invalid input, repeated actions and expected state changes.
  • Source UI review and owner explanations where code alone does not establish intended behaviour.

Environment and decisions

  • Windows/PowerShell, Node.js 22+, npm and a compatible, approved Copilot CLI account. The preview selects GPT-5.4 mini explicitly.
  • Shared decisions about target experience, identity, hosting boundaries and what this migration will not change.
  • A reviewed credit allowance and attempt limit before running generation.
  • A trusted execution environment and an operator able to answer questions and review output.

A Slack workspace export is not application source. The kit does not connect to Slack and automatically discover, download and migrate every installed app. Inventory import and source preparation are operator-led. Source replay executes code, so never treat the local runner as a sandbox for unreviewed customer repositories or production credentials.

From an experiment to a repeatable workflow

A controller around the agent.

The portfolio preview replaces manual coordination with durable app jobs and explicit gates. It does not remove business ownership or pretend every installed Slack app is convertible.

Inventory & scope

Supply source allowlists, owners, dependencies and approved acceptance cases. Missing source and unsupported patterns stay visible as blockers.

Investigate & clarify

Assess actual source, save owner answers and meter app-specific or shared consultation. Reuse approved organisation-wide decisions.

Review the exact plan

Bind local approval to the assessment hash. Unresolved questions and unsupported strategies prevent implementation.

Generate & repair

Use scoped GPT-5.4 mini sessions and reviewed recipes. Keep source rules intact. Feed rejected results into bounded repairs.

Verify independently

Compile and compare expected behaviour, state and audit. A successful model exit is not acceptance; local verification is not deployment.

Handoff with costs

Deliver generated code, gaps and evidence with incremental app/stage costs. Production rollout requires separate engineering and approval.

The preview is sequential and resumable. App workspaces and file-only tools provide scoped work, not a hostile-code sandbox. Only reviewed, trusted source should be replayed.

Who does what at each gate?

1. The engineer defines the portfolio; the controller prepares the evidence

You create an inventory pointing to source jobs and record shared decisions once. init validates the inventory, dependencies and source paths, then copies only the selected files into separate app workspaces. Missing source or an unsupported disposition is visible as a blocker.

On run, the controller prepares the app revision and checks the source baseline before generation. This is a deterministic preparation/checking step, not the model guessing what the original application does.

2. Copilot investigates the supplied source and proposes a Teams plan

The scoped worker reads the source, declared capabilities, acceptance cases and recipe contract. It writes assessment.json: source-line evidence, reusable logic, target surfaces, additional findings, unknowns, blockers and deployment prerequisites.

This investigation is source-based. It does not independently browse a live Slack workspace. If live UI behaviour or an external system needs review, the operator must supply that evidence and make it part of the acceptance process.

3. Owners resolve uncertainty; the conversation is recorded rather than lost

answer records a question's answer, named operator and timestamp. If an existing assessment needs revision, a metered clarify pass incorporates the decisions. Additional app-specific or shared investigation can be run through discuss and is charged to that scope.

Advice does not automatically become an approved requirement. Unresolved questions or blockers prevent plan approval. Conversation outside the runner is an external cost, not silently included in its totals.

4. An operator approves the exact plan, not a vague instruction to “migrate”

The operator reviews the actual assessment, source evidence and baseline, then supplies its hash to approve. Approval permits local implementation of that unchanged plan. Source or approved-plan changes require a new reviewed revision.

These are local named-operator records, not authenticated business-owner signatures or enterprise CI approvals. Production change control must supply that stronger authority separately.

5. Copilot implements the target; the controller rejects incorrect results

The worker adapts the interface and transport while retaining the source domain service. The controller independently checks protected inputs, approved package/configuration, compilation and recipe-specific outcomes. Failed checks become explicit repair feedback within the remaining allowance.

There is no silent model escalation or unlimited retry loop. An exhausted implementation allowance stops the app; an operator can approve a recorded, bounded extension without changing the aggregate budget or source contract.

6. Downstream acceptance can still reject a green local check

The bot replay compares responses, visibility, buttons and state across three synthetic Teams transport variants. The Home checks compare domain responses, state/audit and spoofed client identity, plus syntax/static integration checks. Neither is a real tenant deployment.

Browser, integration, accessibility and owner review remain separate acceptance layers. Use request-repair to record a defect found after a local pass. Use accept only after review, and check to confirm all jobs have intact local verification and complete managed metering. No command here grants production deployment approval.

Worked example: what changes in the delivery bot?

The source owns the rules: look up a shipment, escalate it, allow only the appropriate role to resolve it, reject invalid transitions and avoid duplicate audit entries. The Teams implementation calls that same service rather than asking a model to make those decisions at runtime.

The migration replaces Slack command/action handling with a native Teams command, Adaptive Card actions and private replies. It also has to satisfy the Teams invoke acknowledgement contract. In the fresh batch, a model draft omitted the separate private reply after fixing the acknowledgement; the replay rejected it, and an explicitly approved repair restored both operations.

That is the repeatable part: preserve a reviewed source contract, generate a platform adapter, check exact behaviour and retain the failure/cost evidence. It is not an assurance that any app converts correctly on the first attempt.

What the new runner records

Every model invocation it launches: source assessment, clarification, consultation, implementation and repairs. Resumed sessions contribute only incremental usage; failed attempts stay in the totals.

Missing metering stops new model work. Product development and external conversations remain explicitly unallocated, not silently zero.

Which actions consume model credits?

Source assessment, model clarification, managed consultation, implementation and model repair are metered. Recording an answer, checking status, approving a plan, generating a deterministic report and resuming an already accepted batch do not themselves invoke a model. The controller's own compilation/replay checks are also model-free; external services in an application's code have separate costs and approval boundaries.

Each invocation keeps native usage evidence. A resumed session contributes only its increase in cumulative usage, and unsuccessful attempts remain in the total. Missing accounting blocks new model work. The CLI credit limit is soft: in-flight work can overshoot, and the ledger records that rather than truncating the bill.

A full programme estimate must separately allow for shared tooling, source preparation, outside coordination/review, customer integrations, human effort, infrastructure and rollout. Not every app will fit an existing recipe.

Practical questions

Before you point it at a real portfolio.

Can I give it a Slack workspace URL and say “migrate everything”?

No. v0.2 takes an explicit inventory of source jobs. It does not enumerate installed apps, retrieve vendor source or automatically review the live Slack UI. Start by identifying app ownership, source availability, integrations and business criticality; then select jobs that fit a reviewed recipe.

Can I download the toolkit or finished Teams apps here?

No. This publication is the website and documentation only. Toolkit source, fixtures, generated targets and the ZIP remain private. The case studies explain what was built, how it was reviewed and what it cost, so other engineers can reproduce the approach with their own authorised source and tooling.

Is this a Copilot Studio agent, a single skill file or a hosted service?

No. It is a local Node-based developer kit using GitHub Copilot CLI workers. It includes a custom agent for the older per-app flow, but the portfolio controller supplies the state, gates and accounting. Installing only that agent file does not install the batch workflow.

Does it copy Slack Block Kit directly into Teams?

No. The recipe chooses a Teams surface appropriate to the reviewed source behaviour: native commands, Adaptive Cards or the supported personal-dashboard design. Business decisions stay in the original service. UI redesign is intentional and needs acceptance; pixel-for-pixel conversion is not promised.

Can I use the source examples without provisioning Slack or Teams?

The local regression/replay examples do not need live Slack or Teams registrations. Generating new code does require a compatible Copilot CLI account and allowance. A real-client demonstration needs separately approved tenants, apps, authentication, hosting and client checks; those resources are not bundled.

What happens when an app does not fit or the model gets it wrong?

The app remains blocked, awaits information, or fails verification; it is not counted as a successful migration. Repairs use the same approved scope within the remaining limits. A named operator can record a bounded retry extension, but changing the source contract, recipe or plan requires a new reviewed revision. A local pass can still be rejected by downstream review.

Do the generated examples need an AI model at runtime?

The demonstrated policy and approval decisions are deterministic calls to the reused business service, not model-generated decisions. Copilot is used to perform the migration. A different application's own AI or external-service dependencies would require separate assessment and accounting.

Does a green report mean the application is safe to deploy?

No. Read exactly which checks passed and which behaviours the baseline covers. The kit's approvals are local operator labels, not authenticated business-owner or security approvals. Production identity, durable state, permissions, integrations, accessibility, load, intended Teams clients/channels and operational handover require their own acceptance.

An honest preview

What this does not prove.

  • Not a customer production migration. All demonstrated records, policies and workflows are synthetic.
  • Not every Slack app. The recipes cover defined Node/Bolt and approval-domain contracts. Other stacks and vendor apps need another reviewed path.
  • Not production acceptance. Durable state, SSO, customer integrations, multi-person isolation, load and comprehensive accessibility/client testing remain separate work.
  • Not transferable live proof. Earlier live examples do not establish that a newly generated portfolio revision is installed in Teams.
  • Not a public data dump. Tenant identifiers, credentials, private conversations, raw event logs and unsanitised screenshots are deliberately excluded from this page.
